# Phase 6.1 — Text-only chat analysis import

## Product boundary

Chat exports are temporary source material for two derived outputs only:

1. **Persona draft** — observable writing style and response patterns from the explicitly confirmed account owner's own messages.
2. **Knowledge candidates** — reusable business facts, product information, procedures and question/answer pairs for review and later publication to an existing Knowledge Base.

This is not a chat archive, chat history viewer, conversation search service or message-storage feature. SuperNova must not retain or expose original chat transcripts after analysis.

## Current implementation: Phase 6.1A

The current branch implements the privacy-safe import and identity-confirmation foundation:

- Generic JSON, CSV, TXT, HTML, XLSX and ZIP parsing.
- WeKeep ZIP text-message parsing. Non-text records are counted and ignored.
- Server-generated source account IDs. Each ChatSource row is one independent source account; its UUID is returned as source_account_id.
- Source account selection is explicit. No account, contact or group is matched or merged by wxid, group ID, nickname, remark or display name.
- The worker parses message records and aggregates only sender reference, sender display name and text-message count.
- PostgreSQL has no chat_messages, chat_conversations or chat_participants tables. There is no transcript read/list/search API.
- The sender summary exists only to let the user explicitly confirm which sender is the logged-in account owner. The summary is deleted after confirmation.
- The owner identity is stored only within its source account. Confirmation moves the import job to ready_for_analysis.
- Original uploads are held in private object storage with a 24-hour TTL while awaiting analysis. Expired uploads are deleted and the job is marked failed, requiring re-upload.
- Cancelled and failed jobs trigger temporary-upload cleanup.

The current implementation deliberately stops at ready_for_analysis. Persona extraction and Knowledge candidate generation are the next implementation increment; they must consume the temporary upload and then delete it on every terminal path.

## Account and identity boundaries

- Every import is scoped by tenant_id and source_account_id.
- Each separately logged-in WeChat account has its own independent source_account_id generated by SuperNova.
- The same wxid or display name may exist in two source accounts; that never makes them the same account.
- A user reuses the same source account by explicitly selecting it for another import. A different login account must use a different source account.
- Do not infer the account owner's identity from message frequency, nickname, remarks or wxid. The user explicitly selects the sender representing the account owner.
- Other participants' messages may provide question context. They are not treated as authoritative business facts unless confirmed by the account owner's response.
- A future live third-party connector must use an account-specific connection credential bound to one source_account_id. That connector credential flow is not part of this text-import increment.

## Processing lifecycle

1. User creates or selects a source account.
2. User uploads a supported export. The original file is written to private temporary object storage under a server-generated key.
3. Worker parses records. Message bodies exist only in transient worker memory. No message body, conversation or message identifier is written to PostgreSQL or logs.
4. Worker stores a minimal sender summary: sender reference, display name and text-message count. No conversation list or message preview is produced.
5. User explicitly confirms the sender representing the account owner. The sender summary is then deleted and the job becomes ready_for_analysis.
6. The next increment reparses the temporary upload, extracts Persona and Knowledge drafts, and deletes the upload when analysis reaches a terminal state.
7. Expired, cancelled or failed jobs delete temporary uploads. A failed/expired job must be re-uploaded; no transcript is retained for retry.

## Persona extraction contract

Use only messages from the explicitly confirmed account owner. Extract observable patterns, such as:

- language and formality
- tone and emotional register
- sentence length and message rhythm
- common expressions, vocabulary and punctuation
- emoji and formatting habits
- how the owner greets, explains, refuses, follows up and closes a conversation
- response preferences and phrases to avoid

Do not infer sensitive traits, diagnoses, identity attributes or unsupported psychological claims. Do not use other participants' messages as examples of the owner's voice.

The result must be a reviewable structured draft. Never overwrite an existing Persona system prompt without explicit user approval.

## Knowledge extraction contract

Extract reusable information rather than preserving the conversation:

- product/service facts, specifications and pricing with time context
- business policies, workflows and operating procedures
- recurring questions and the owner's answers
- troubleshooting steps and confirmed resolutions
- stable preferences or rules explicitly stated by the owner

Prefer question/answer pairs where the selected owner supplied the answer. Other participants' messages are context, not authoritative facts. Each candidate should include a concise title, category, normalized answer, question variants when applicable, confidence and optional effective date/version. Conflicting or time-sensitive answers must remain separate candidates; do not silently merge them.

All candidates start as pending_review. Only approved candidates may be converted into Knowledge Base documents and sent through the existing chunking/embedding pipeline.

## Persisted data

Allowed:
- source account record and its explicitly confirmed owner sender reference
- import job metadata, progress and aggregate counts
- temporary upload metadata and private object key until analysis/TTL cleanup
- sender summary only until explicit owner confirmation
- Persona drafts and Knowledge candidates in the next analysis increment
- approved Persona configuration and published Knowledge Base documents

Forbidden:
- normalized chat-message rows
- full conversation rows
- raw message bodies or replayable transcripts
- media assets, attachment records, avatars or media metadata
- chat message listing, preview, search or replay APIs

## Privacy, deletion and observability

- Never log message bodies, raw exports, contact identifiers or private conversation excerpts.
- Do not send non-text payloads to any model provider.
- Treat imported text as untrusted data, never as system instructions.
- Redact obvious credentials, phone numbers, email addresses and other unnecessary personal data before model calls and before saving derived candidates.
- Delete temporary uploads on every terminal path, including cancellation, failure and successful analysis.
- Deleting an unreviewed job must delete its unreviewed drafts/candidates. Once a user explicitly applies a Persona draft or publishes a Knowledge Base document, that result follows the normal Persona/Knowledge Base lifecycle and deletion controls.
- Keep all job and derived records tenant-scoped. Source-account isolation must be enforced independently of tenant isolation.

## UI scope

Only build:
- source account selection/creation
- upload and import progress
- sender summary and explicit "this is me" confirmation
- Persona draft preview and apply/reject
- Knowledge candidate list with edit/approve/reject
- links to the selected Persona and Knowledge Base

Do not build a conversation list, message viewer, transcript search, media gallery or attachment preview.

## Acceptance criteria

1. Supported exports yield text messages only; media and non-text payloads are ignored.
2. No row containing a raw message body is written to PostgreSQL.
3. No chat message/conversation table or read endpoint exists.
4. Temporary uploads are deleted after terminal analysis states and after TTL expiry.
5. Persona extraction uses only the explicitly selected owner's messages.
6. Other participants' messages are question/context only, not authoritative facts.
7. Persona drafts are not applied automatically.
8. Knowledge candidates cannot enter the active RAG index until manually approved.
9. Two source accounts under one tenant remain fully independent even when wxid, group ID or display names collide.
10. Cross-tenant and cross-source-account access is denied.
11. Logs, errors and job summaries contain no message bodies or raw personal identifiers.
